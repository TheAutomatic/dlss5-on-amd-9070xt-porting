# 网络更快，D3D↔HIP等待会更慢吗？（速度研究，2026-10-04）

**这次正常fence协议、memset占位负载的小探针没有支持固有规律：网络越快，绝对剩余开销反而更小；它占总时间的比例更大。** 不否定Daniel特定宿主/驱动的性能现象，原引文是用户转述，未取得其同时段分段计时。此次不研究崩溃，不做TDR/自旋/故障恢复，不改生产或游戏配置。

## 本次小测

沿既有handoff探针，只允许mode1（D3D Signal→HIP异步Wait→工作→HIP Signal→D3D队列Wait），两帧在飞。D3D仅固定两条timestamp列表，HIP一个memset（64/256/2048MiB），不是实际NN。各40帧、弃4；GPU前查无游戏并拿gpu.lock，结束释放。

D3D前后时间戳同一时钟，得到**含HIP工作与交接的总区间**。HIP event另量工作时长，差分只能叫剩余（含调度、上下文/队列切换、CPU提交不足等），不是纯fence等待。

|到达模式|HIP工作ms|D3D总区间ms|差分剩余ms|剩余/总区间|
|---|---:|---:|---:|---:|
|密集，轻|.051|.146|.095|65%|
|密集，中|.449|.582|.134|23%|
|密集，重|3.562|3.774|.212|6%|
|稀疏，轻|.078|.269|.191|71%|
|稀疏，中|.436|.663|.227|34%|
|稀疏，重|3.490|3.726|.237|6%|

稀疏请求Sleep8ms，Windows实际CPU每帧约15.5ms，不能称精确8ms。稀疏比密集提交的剩余更大，没有看到“到达越快越停顿”的必然性；这个差额不能唯一归因频率/唤醒/调度，因为未分别控制它们。短样本不做长尾普遍结论。

**计时坑确实存在：**首扫HIP event返回负/近零工作时间，物理上无效，首扫差分全部弃用。按已有net-timing修法，end record后立即非阻塞hipEventQuery，最后六档0负/零，才用于表。中间一次构建失败误复用旧产物的批次也弃用。日志、有效CSV、source/binary hash留存，没有拿坏计时支持机制结论。

## 为什么Daniel现象仍可能真

正常依赖关系只改变持续时间，不因为NN变快就改变箭头：

```mermaid
flowchart LR
 P["D3D生产输入并Signal"] --> H["HIP Wait→网络→Signal"]
 H --> C["D3D Wait→消费输出"]
 C --> N["下一帧生产者"]
```

1. 固定切换税占比上升：例如剩余.1ms，计算由8ms减至2ms，占比自然涨，整帧加速小于单核加速；这不等于绝对等待涨。
2. **CPU没来得及把工作/结束Signal提交完**，GPU前段更快就更早撞到未提交窗口，idle可增长；最终瓶颈转为CPU提交。已有outside-net具体实证：输入copy .22→.08ms，串行的剩余 .21–.24→.27–.31ms，总wall几乎不动；正确流水线帧间隔9.71→9.57ms却兑现收益。不是fence本身变慢。
3. 到帧节奏/在飞数量也变化：CPU更快地排工作、帧队列背压、稀疏调度冷启动、HIP批次提交时机都可能改变尾部空泡。生产桥post-signal非阻塞Query曾改善串行 .01–.12ms、流水线中性，这是具体可动的提交问题，不能说HIP一概无解。
4. **同queue原生后端确实能减少切换税**；但同GPU的第二条D3D队列也有约同量级税，故不是全由HIP API造成。Vulkan只有真的录进同条命令流才有这个优势，另开互操作队列仍要同步。

若要验证Daniel特定版本，最小补数据是同场景、快/慢版本的GPU NN时长、同D3D钟总区间、CPU Enqueue/Signal提交时刻、在飞数与实际帧间隔；先检查event计时有效。无需重做所有优化。这轮已有案例+有界小测够用，停止继续找所有驱动问题。
