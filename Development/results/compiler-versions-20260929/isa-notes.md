# 指令差异的读法

`active-kernels.csv` 覆盖最新900/1080 trace并集的43个活跃kernel/module对；`family-static.csv` 按每族独立函数体求和。静态计数不乘派发数、窗口数或循环次数，不能当每帧动态指令数。VMEM列是指令条数，不是DRAM字节量；WAIT沿用项目分类，含wait/nop/delay/clause/barrier/sleep。

## 现有手写绕法没有因版本变化自动消失

在三组代表核上，COMGR2/公开21/公开22与现役COMGR3的下列静态数量相同：

|核|max_num|med3|half转换（含pk_rtz）|div_scale/fmas/fixup|setreg|
|---|---:|---:|---:|---:|---:|
|c32_wave1_chain|0|40|96|0|34|
|c64_wave2_bi_bo|16|64|104|0|84|
|c128_wave2_bi_bo|16|64|104|0|84|

生产源码已经显式用了fmed3、fmaf(x,y,+0)、有界倒数和MODE短段。因本轮约束是同源码，没有撤销这些绕法再看各编译器能否自行推回；因此不能宣布某版本“自动修好了”这些模式。上表说明这些具体站点没有出现明显的转换/clamp/div-helper/setreg数量改进，也不是证明全网每处都相同。

setreg统计涵盖所有setreg类指令；只凭条数相同不判断调度边界或空MODE段是否相同。完整七组回归负责实际输出，不能用统计替代数值检查。

## LLVM22：代码变短的重要原因是尾部重新形成循环

`split_mix_blocked_h16w_m32` 静态指令1047→403，WMMA仍8条；单看总数很像砍掉六成工作，但尾部实际上从完全展开变成两个四轮循环：

- `.LBB76_7`：`s[10:11]=7`，每轮加8，比较39，执行4轮。
- `.LBB76_10`：`s[2:3]=7`，同样加8到39，第二个token片段执行4轮。
- 原静态64条FP8转换/RTZ转换/FP8反转换/float写出，变成16条静态，每轮执行后仍合64条；不能把16/64解释成省了75%的该类运行工作。
- 增加`v_movrels_b32`与m0寄存器间接索引，代码体积、寄存器调度、循环控制是新的取舍，只有实测能决定快慢。

原始片段见 `llvm22-tail-loop-evidence.txt`。ViT expand的类似尾部从64/128份降到16/32份，也伴随新寄存器间接寻址；这里仅作同类指纹，不把所有其他核都归因到同一个循环。

## 资源并不随版本单调改善

公开21与22的C128融合核部分VGPR从159降到148～156；C256整块的公开21从154升179，公开22升得更多（整族最高198）。COMGR2的C128/C64静态体积较大。三套在43个活跃核中都没有新增VGPR/SGPR spill；LDS/private段也没有新增。更低VGPR不自动等于更快，更短代码也不自动等于更少执行。

此次比较的是实际可用的编译器管线：COMGR2、COMGR3和公开LLVM的独立复刻，不是控制所有内部补丁和默认参数后对一个pass做因果实验。核源码与用户指定编译选项固定；没有为某一版本另调配方、算术或flags。
