# C64/C128/C256 核本体差距：逐核对 mochizuki fswin，第一刀 W2_UP_LOW_BYTES（2026-10-01）

**结论先行**：900 档 C64/C128 的差距不是均匀摊在每个块上，而是**集中在链的两端**。链内部的块（`*_wave2_bi_bo`，字节进、字节出），我们约 82µs（C64）/ 59µs（C128），和他每层的均摊时间同量级。多出来的钱在三类"边界核"上：链尾写 f32（`*_bi`），比链内块多 22µs（C64）/ 11µs（C128）；上采样首块（`*_up`），多 34 / 24µs；独立的下采样池化（36 / 22µs），他把这一步折进了持久化核。第一刀选"解码链尾写 f32、下一级 Up 再读 f32"这一处：链尾的值本来就在 E4M3 格点上（post 0 = F(Hrtz(v))），改成写字节、Up 读字节，数值上没有任何差别。**19 组 SAME，三轮 ABBA 两档全快，p99 两档都更好，已收并装机。**

## 1. 组织方式对照（900，µs；我们 = kernel-map-v3 单核中位；他 = 同链逐派发计时，含空隙）

他的 `fswin_t.comp`（5114 行，持久化 `NR_PERSIST`）的组织方式：
- 每段一个派发，工作项是（层, 窗口），靠依赖表领取（`NR_PERSIST_DF`），下采样当作最后一层（`NR_PERSIST_DS`），上采样当作第一层的序章（`NR_PERSIST_UPS`）。
- 一个 WG 做一个窗口的整个块，按头分 wave（`NR_HWAVES`）。块内 LDS 只放 e4m3 的 x/y（`lds_x/lds_y`）。
- 残差流全程 e4m3（`NR_R_E4M3`），块之间、段的两端都没有 f32。
- **数值上他放弃了与 NVIDIA 逐位一致**（`NR_ACC_F16`：f16 累加；一次舍入的 e4m3 量化；f16 蝶形归一化），源码注释写明了。

我们每个块一个派发，一个 WG 负责一个窗口的一个块，按头分 wave。f32 累加，按 NVIDIA 的顺序。链内残差已经是字节（`mh_byte_stream`），只有链的两端还是 f32。

能逐位追的是**数据格式和边界组织**，累加精度这部分追不了。负账里已经试过的不再做：C64/C128 持久化、W16 推到 C64/C128、下采样融合（`resample-fold`，逐位但 3/3 轮都慢）。

## 2. 第一刀：`W2_UP_LOW_BYTES`（c64-wave2 模块宏 + 宿主）

- 解码链尾（块 55 = C256 上，块 61 = C128 上）的 post 为 0，输出 F(Hrtz(v))，本来就在 E4M3 格点上。现在直接写字节，用的是已有的 `*_bi_bo` / `c256_attn_wave_bo` 字节出口，它们在 post 0 时存 q8(Hrtz(v))，和 F 的结果是同一个字节。
- Up（`c128_wave2_up` / `c64_wave2_up`）的低分辨率输入改成读字节：`(_Float16)cvt_f32_fp8(byte)`，得到的 f16 操作数和原来 `(_Float16)f32` 一模一样。新增导出 `c64/c128_wave2_up_lb`。宿主只在模块里有 `_lb`、下一级走融合 Up、链尾没有被跳块时才启用；否则走老路径。
- 块 65（C64 上的链尾）的消费者是 C32UpBody（c32-wave1），本轮没有改，还是 f32。
- 静态检查：lb 模块和配方 prod 相比，原有函数逐条相同，只多出 2 个 `_lb` 函数。prod 与现装 48B6FA8B 的 `.text` 相同（文件哈希不同，是宏顺序造成的）。final（配方重编）的 `.text` 与实测的 lb 相同。
