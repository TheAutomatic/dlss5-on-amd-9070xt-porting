派发来自真实trace，包含init/run/recover；常态recovery一WG读abort后直接退出。正常核与队列核的VGPR/LDS相同，没有spill，SGPR C128 25→40、C64 30→45。驱动API返回C64最多8个64线程WG、C128最多4个128线程WG（每multiprocessor512/2048线程），普通/队列均25%；不是GPU profiler实测活跃率。双架构元数据见 `resources.json`，Windows9070查询见 `raw/occupancy.csv`。

**为什么这次不快：** 900 C256原来内六层12次派发降到3次，单边省9次；1080六层6→3省3次。小通道现役已逐层融合，C128四层4→3只省1次，C64两层2→3反增1次。与此同时窗口任务更多，需要设备队列/原子依赖推进；算术、VGPR/LDS及理论驻留能力都没减少。实测收益不足以摊薄这套管理开销。这里没有逐周期stall分解，不把上述结构解释写成精确瓶颈占比。

C256保持开启；新段内部替代PDL，段边界正常stream顺序，其余PDL继续保留。C128 block56/C64 block62上采样融合首块不动，C32上采样融合首块也不动，只合各stage内部四/两层。详细边界与计时方法见 [method.md](method.md)。

- 四候选各7用例×EXACT/AE×12帧，共**672候选帧**命中09-28 float FMA（0.36）golden，AE336行逐字段同；720尺寸确认原路回退。

- 回绕用ticket start=4294967290、limit=1024：每12帧36次reset（新增小stage与两个C256段都实际回绕），无错误/回退。超时只针对小通道，阻止初层发布后继；无诊断同步，约100ms到期后GPU串行按层重算，恢复计数=1、errors=1、实例禁用=1。编码器故障发生在C256之前，runs=1；解码器在两个C256之后，runs=3，确认不是只测了旧C256故障。
- 所有正常计时均fallback/errors/disabled=0，1000帧A确实2000次C256段运行，P确实3000次（三段），不是意外未启用候选。
