# C512 跨块就绪队列（方案 P）：上限探针为负，停手（2026-10-01）

**结论**：不做 P。先测"跨块重叠"能拿到的**上限**：把编码块 23–30 改成 8 个**互相独立**的块体（都读块 23 的输入，round-robin 到 8 条额外 stream，彼此没有依赖、全部可并行）。这比任何带依赖的就绪队列都宽松，只用来计时，输出本来就是错的，不是候选，也不做逐位验证。结果三轮 ABBA 全部**变慢**：

| 轮 | 900 均值 ms | 1080 均值 ms | 900 p99 | 1080 p99 |
|---|---|---|---|---|
| 1 | 7.5800 → 7.7849（+0.205） | 10.3779 → 10.7060（+0.328） | 7.856 → 8.138 | 10.685 → 11.064 |
| 2 | 7.6183 → 7.8424（+0.224） | 10.3937 → 10.7244（+0.331） | 7.877 → 8.234 | 10.705 → 11.090 |
| 3 | 7.6116 → 7.8585（+0.247） | 10.3979 → 10.7070（+0.309） | 7.845 → 8.282 | 10.666 → 11.069 |

条件：同一份 HEAD 源码编出的 A/X 两个宿主，都用剑星现装的 31 个模块（add-on 6d059845），flags 与 c512-compact-vt 的 regression.ps1 相同；每槽 1000 帧，弃前 200 帧，A-X-X-A。原始数据在 lab `D:\DLSSNR-Lab\hip-backend\c512-xblock-queue-20261001`，汇总在 `abba-ceiling-k8.txt`。

## 为什么停
- 依赖全部拿掉、8 块完全并发，整帧仍然慢 0.2–0.33ms。所以 P 的收益上界不是正的，何况 P 还带真实依赖、每帧约 2.5 万（900）/ 3.5 万（1080）个任务的领票和计数开销。设计稿估的"~5000 任务/帧"低了 5–7 倍：mix 376、ffn 752、proj 752、attention 448/560、aproj 752，每块约 3.1k 个任务。
- 变慢的原因推断如下（没有计数器，拆不开）：多个 C512 块同时驻留，互相抢 L2/MALL（每块权重约 2.2MB，中间张量每块数 MB）；板功耗钉在 325W，重叠换来的并发以降频的形式还回去。这与 09-25 pdl-c512 的结论一致：tile 旗子单独开 −0.16ms，和其他族叠加后为 0。此外，多 stream 的事件同步也有少量开销。
- 探针用了 8 条 stream。stream 数少一些（k=2）也许不会变慢，但上限已经说明"让 C512 块彼此重叠"在这张卡上不赚钱。A（块内 attn→aproj 队列）是同一机制的子集，一并不建议。
- 设计稿说"PDL 只填空隙、P 重叠延迟链"，这个区分并不成立：pdl-c512 已经是按 tile 放行的跨核重叠。

没有新增宏、模块或宿主改动，所以 RE9 runtime、三个模板和 CONFIGURATION.md 都没有动。探针脚本在 `Development/HIP/experiments/c512-xblock-queue/`。
