# 1080 档 PDL 状态 `pdl=1/0`：是设计如此，重测后结论不变（2026-10-02，光派单，子代理，未改生产、未装机）

## 原因
- GetStatus 里的 `pdl=A/B`：A 表示 `DLSS5_HIP_PDL` 有没有请求（opt.pdl），B 表示这个实例有没有真的发出过 any-order 派发（`bridge->PdlActive()` = `PdlCalls()!=0`）。
- PDL 只挂在 C64/C128/C256 的**分体**路径上（FFN `_pdl` 加 attention `_pdl`）。C64/C128 在 wave-owned 下两档都走整块融合，所以本来就没有 PDL。C256 在 1920×1152/1088 走整块融合，这是 `hip_reference_network.h:479` 的条件，来自 09-28 的 fcc11736（整块在 1080 快 1.65%，900 持平，"900/720 保持原分体 PDL"）。所以 1080 档一次 any-order 都没有，状态显示 `1/0`。这不是 bug，不是尺寸或 16384 槽的限制（那个限制只影响 free-res 下超过 4.19M 像素的尺寸），也不是缺导出或白名单的问题。add-on 走的是同一份宿主代码（桥接共用），在 1080 同样没有 PDL。
- 这个基线已经变了：09-29 起 C256 持久化（SWIN_RUN）接管了 16–21、49–54，还走 Body 的 C256 只剩 15/22/48/55 这 4 块。所以按要求重测。

## 重测
候选（`HIP/experiments/pdl-1080/candidate.patch`）：在 1080 档，只有 C256 持久化启用时（`!SpEnabled(256,block>=40)`），这 4 块改走分体+PDL；没有持久化时仍然走整块。RE9 runtime（rt-old 77A35681 = main，rt-new 562F9698），装机 62 模块，RE9 环境（PDL=1，SWIN_RUN=1）：
- 逐位：720/900/1080 的 old/new 哈希全部相同（88106a93 / b2980ada / 758674a8）。1080 状态从 `1/0` 变成 `1/1`。smoke 0，SP errors 0。
- ABBA（400 帧 ×3）：900 −0.004/−0.002/−0.011（持平，这档本来就没变）；**1080 +0.076/+0.077/+0.049ms，三轮全慢**。
- 结论：即使只剩 4 块，整块融合仍然比分体+PDL 快，按规矩不收。19 组 add-on 验证和装机没有做（三轮都慢，已经可以判否）。原始输出见 `rt.txt`。
